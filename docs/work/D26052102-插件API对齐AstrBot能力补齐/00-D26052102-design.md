# D26052102 插件 API 对齐 AstrBot 能力补齐设计

更新时间：2026-05-21 10:46 +08:00

## 场景

- Scene：`uth-design`
- Mode：`design-authoring`
- 目标：在明确不做 Web API 注册、平台适配器注册、DB 直连、文本转图和 HTML 渲染的前提下，给剩余 AstrBot 插件 API 缺失能力制定顶层设计与落地顺序。
- 输出：任务包 Design。源码实现、Todo 拆分、Worker prompt、评审和 Git 写入均不在本轮执行。

## 用户确认决策

2026-05-21 用户确认：

- 不暴露 AstrBot 风格别名；插件 JS API 只使用 ElymBot canonical host API 命名。
- 网络能力必须走宿主代理，不给插件直接网络客户端。
- `hostApi.callLlm` 默认绕过插件 LLM hooks，避免 hook 内调用 LLM 后递归触发自身 hook。
- Todo 需要把本设计中的能力全量拆出；实际派发顺序由用户后续决定。

## 背景

上一轮差异扫描确认：当前插件 V2 已经具备 message / command / regex / lifecycle / LLM hook / tool 注册、settings 读取、plugin/session KV storage、ToolSource 聚合和 LLM pipeline hook。`差异.md` 中关于 KV 与 loaded hook 的部分已经过时；当前缺口主要集中在插件主动调用宿主能力，而不是基础注册能力。

当前代码事实：

- `PluginV2BootstrapHostApi` 当前向 QuickJS bootstrap 暴露 registration、lifecycle alias、LLM hook、tool、log、metadata、settings 和 storage。
- `ExternalPluginHostActionPolicy` 中 `call_model`、`network_request`、`read_private_data`、`write_private_data` 仍是 declared-only；当前开放执行的 host action 只有 `send_message`、`send_notification`、`open_host_page`。
- `PluginProviderRequest`、`RuntimeLlmOrchestratorPort` 与 LLM hook pipeline 已有 provider/model/request/response DTO，但没有面向插件的直接 `hostApi.callLlm`。
- `FutureToolSourceRegistry` 已聚合 MCP、Skill、Active Capability、Context Strategy、Web Search provider；插件自身 `registerTool` 仍不能注册 reserved source kind。
- `ContextStrategyToolSourceProvider` 已暴露 `compress_context`，但执行返回 `context_compress_not_implemented`。
- `PluginV2FilterEvaluator` 对已声明 filters 按顺序 AND 求值，暂不支持 OR / NOT 组合表达式。

## 需求边界

本设计纳入的剩余能力：

- 网络请求代理：`hostApi.fetch` / `hostApi.request`
- 直接 LLM 调用：`hostApi.callLlm` / `hostApi.llm.generate`
- Provider / model 只读查询
- 会话消息发送：先做当前事件会话，后续再扩展明确授权的目标会话
- 会话历史只读查询
- 插件自注册定时任务回调
- 插件侧流式输出
- 富消息链 / 附件 / mention / reply 这类跨平台消息结构
- Tool Loop Agent / Agent 能力注册
- filter OR / NOT 组合表达式
- 已存在 `compress_context` 的落地实现

本设计明确不纳入：

- Web API 注册或让插件暴露 HTTP endpoint。
- 平台适配器注册或让插件新增 QQ / App Chat 之外的新 adapter。
- DB 直连、DAO 暴露、SQL 执行或 raw Room transaction。
- 文本转图、图像生成、HTML 渲染或截图渲染。
- 恢复 static repository facade、手写 runtime subgraph、service locator 或生产 global registry。
- 修改插件市场协议之外的发行/安装策略。

## 总体设计原则

1. 宿主代理优先：插件不得直接碰数据库、provider secret、adapter socket 或 Android service；所有能力经 Hilt-owned port 和 `PluginHostCapabilityGateway` 代理。
2. 当前上下文优先：会话发送、历史读取、streaming、rich message 第一阶段只允许当前事件会话，避免一开始就开放跨会话群发。
3. 权限四层收敛：manifest 声明、用户授权、trigger whitelist、运行时策略校验必须同时通过。
4. JS API 使用 ElymBot canonical host API 命名，不暴露 AstrBot 风格别名；对齐目标是能力边界和宿主代理语义，不复制 AstrBot 架构。
5. 异步能力先打地基：网络、LLM、history、cron、streaming 都需要 QuickJS callback 能等待宿主异步结果；不能用无限阻塞或主线程同步调用糊过去。
6. 按可验证切片落地：每个阶段必须能用单测和 architecture/source contract 独立验收，不能把 Agent、streaming、rich message 和 LLM 一次性混成不可回归的大改。

## 核心架构

### 1. Host API Facade

在 `feature/plugin/runtime` 内新增 V2 专用 facade，作为 QuickJS bridge 与宿主能力之间的唯一入口：

- `PluginV2HostApiFacade`
- `PluginV2HostApiRequestContext`
- `PluginV2HostApiPermissionPolicy`
- `PluginV2HostApiAuditLogger`
- `PluginV2HostApiAsyncBridge`

Facade 只依赖 domain/api port，不直接依赖 Room DAO 或 feature implementation。生产 wiring 放在 `app-integration` 的 Hilt module；测试使用 fake port。

建议能力分组：

- `network`：网络代理和响应大小治理。
- `llm`：Provider 查询、模型查询、直接调用、usage 返回。
- `message`：当前会话发送、streaming、rich message 编码。
- `conversation`：当前会话历史读取。
- `schedule`：插件自注册 cron callback。
- `context`：上下文压缩。
- `agent`：后置 Agent 注册与 tool loop。

### 2. QuickJS 异步桥

当前 QuickJS bootstrap 支持 async bootstrap completion，但 event callback 的宿主调用仍以同步 `JSCallFunction` 为主。P0 实现前必须补一层异步桥：

- JS 侧 `hostApi.fetch(...)`、`hostApi.callLlm(...)`、`hostApi.conversation.history(...)` 返回 Promise。
- Kotlin 侧将宿主 IO / LLM / repository 读取放到受控 dispatcher，带 timeout、cancellation 和 structured error。
- callback invocation 需要等待 Promise settle，并把 rejection 记录到 plugin runtime log。
- 如果 QuickJS wrapper 无法安全创建原生 Promise，内部可用 thenable/polyfill 适配，但公开 API 仍保持 `await hostApi.xxx(...)`。

验收重点不是 API 名称，而是事件 handler 能实际 `await` 宿主能力并继续生成结果。

### 3. 权限与审计

新增或收敛 well-known permission id，兼容旧 manifest 自定义权限：

- `network_request`
- `call_model`
- `provider_read`
- `send_message`
- `conversation_read`
- `schedule_manage`
- `message_stream`
- `rich_message_send`
- `context_compress`
- `agent_run`

每次调用都记录：

- `pluginId`
- `api`
- `permissionId`
- `conversationId` / `platformAdapterType`
- `requestId`
- `succeeded`
- `failureCode`
- `durationMs`

失败进入现有 `PluginFailureGuard` 或 V2 scoped failure 体系；权限拒绝、限流、超时、超大小应返回 structured error，不让 QuickJS 侧拿到宿主异常堆栈。

## 能力设计

### P0-1 网络请求代理

JS surface：

```javascript
const response = await hostApi.fetch({
  url: "https://example.com/api",
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ q: "hello" }),
  timeoutMs: 10000
})
```

设计：

- 通过 `RuntimeNetworkTransport` / OkHttp 路径执行，不给插件直接网络客户端。
- 默认只允许 `http` / `https`，禁止 `file`、`content`、`intent`、localhost 和私有网段，除非后续显式加开发者开关。
- manifest 可声明 domain allowlist；无 allowlist 时只允许用户明确授权的低风险外网请求。
- 响应体大小默认上限 1 MB；超限返回 `network_response_too_large`。
- 返回 `status`、`headers`、`bodyText`、`bodyBase64`、`contentType`、`elapsedMs`。

落地评估：优先级高，难度中。现有网络抽象足够，主要工作在权限、域名策略、QuickJS async 和测试。

### P0-2 Provider / Model 只读查询

JS surface：

```javascript
const providers = await hostApi.providers.list()
const models = await hostApi.providers.models({ providerId: "openai" })
```

设计：

- 只返回 provider id、display name、enabled、model id、capability、当前可用状态。
- 不返回 API key、base URL secret、headers secret、内部 credential。
- provider/model 数据经 `feature/provider/api` 或 app-integration adapter 暴露给 plugin runtime。

落地评估：优先级高，难度低。它是 `callLlm` 前置能力，也便于插件做模型选择 UI。

### P0-3 当前会话发送消息

JS surface：

```javascript
await hostApi.message.send({
  text: "处理完成",
  markdown: false
})
```

设计：

- 第一阶段只允许当前 `PluginMessageEvent` / command / LLM hook 的 session。
- App Chat 与 QQ 分别通过现有平台回调或 plugin dispatch service 的 follow-up sender 实现。
- out-of-band schedule 场景必须显式携带 schedule 绑定的 `conversationId`，并通过 `send_message` 权限。
- 任意目标会话群发不在 P0 开放。

落地评估：优先级高，难度中。已有 `sendFollowup` 和 host builtin `send_message` 可复用，但要统一为插件主动 API，并补权限与当前会话约束。

### P0-4 会话历史只读查询

JS surface：

```javascript
const history = await hostApi.conversation.history({
  limit: 20,
  beforeMessageId: event.messageId
})
```

设计：

- 只读当前会话，默认 limit 20，硬上限 100。
- 返回 message id、role/sender、text preview/full text、message type、timestamp、attachment refs。
- 附件只返回宿主可控 URI/ref，不暴露数据库主键以外的内部结构。
- 未来跨会话读取需要单独权限和明确 UI 授权，不并入 P0。

落地评估：优先级中高，难度中。需要从 conversation/chat API 取数，不能让 plugin runtime 直连 Room。

### P1-1 直接 LLM 调用

JS surface：

```javascript
const result = await hostApi.callLlm({
  providerId: "openai",
  modelId: "gpt-4.1-mini",
  messages: [
    { role: "user", text: "总结这段话" }
  ],
  temperature: 0.2,
  maxTokens: 800
})
```

设计：

- 通过 `PluginV2HostLlmPort` 调用 provider runtime；默认不再进入插件 LLM hook pipeline，避免插件在 hook 内调用 LLM 后再次触发自身 hook 递归。
- 可选 `runPluginHooks` 第一阶段不开放；后续如需要，应加 recursion depth、cost guard 和 trace id。
- 使用现有 `PluginProviderMessageDto`、`PluginLlmResponse`、usage DTO 作为内部模型。
- 默认非流式；streaming 与 `message.stream` 在 P2 统一处理。
- 超时、token 上限、调用频率、并发数由 host policy 控制。

落地评估：优先级高，难度中高。DTO 和 provider 管线基础存在，难点是 async bridge、递归治理、成本/限流和错误语义。

### P1-2 上下文压缩

JS surface：

```javascript
const compressed = await hostApi.context.compress({
  conversationId: event.conversationId,
  maxTokens: 1200
})
```

设计：

- 补齐 `ContextStrategyToolSourceProvider.invoke()`，让 `compress_context` 不再返回 `context_compress_not_implemented`。
- 内部复用 `callLlm` 的 host LLM port，但使用固定压缩 prompt、明确输入消息窗口和输出 schema。
- 该能力默认 host-internal；插件公开调用需要 `context_compress` 权限。

落地评估：优先级中，难度中。它依赖 `callLlm`，不应先于直接 LLM 调用落地。

### P1-3 插件自注册定时任务回调

JS surface：

```javascript
hostApi.registerScheduledHandler({
  key: "daily-summary",
  cron: "0 9 * * *",
  conversationId: event.conversationId,
  handler: async (event) => {
    await hostApi.message.send({ text: "今日摘要" })
  }
})
```

设计：

- bootstrap 注册 schedule descriptor，runtime 编译为 `PluginTriggerSource.OnSchedule` handler。
- Cron repository 保存 `pluginId`、handler key、cron/runAt、target conversation、enabled 状态。
- 插件 disable / uninstall 时暂停或删除对应 job；插件升级后按 handler key reconcile。
- scheduled wakeup 进入 V2 dispatch，不再走 legacy `on_schedule` 兼容口径。

落地评估：优先级中，难度中。Cron 与 Active Capability 已有基础，主要工作是 plugin handler 持久化、生命周期同步和 schedule target 权限。

### P2-1 插件流式输出

JS surface：

```javascript
const stream = await hostApi.message.openStream({ markdown: true })
await stream.append("第一段")
await stream.append("第二段")
await stream.close()
```

设计：

- 当前会话内创建 host-managed stream handle。
- App Chat 可以先做本地 conversation pending message append/update；QQ 若 adapter 不支持编辑消息，则降级为分段发送或最终一次发送。
- stream handle 必须有 max duration、max chunks、max bytes 和 cancellation。
- LLM streaming 与插件手动 streaming 共用 message stream abstraction。

落地评估：优先级中，难度中高。核心风险是 App Chat / QQ adapter 体验不一致，因此应晚于 P0 主动调用能力。

### P2-2 富消息链

JS surface：

```javascript
await hostApi.message.send({
  chain: [
    { type: "text", text: "看这里：" },
    { type: "mention", userId: "123" },
    { type: "image", uri: "plugin://workspace/exports/a.png" }
  ]
})
```

设计：

- 定义 `PluginMessageSegment`：`text`、`image`、`file`、`mention`、`reply`、`card`。
- App Chat 先映射到 `ConversationAttachment` 与 markdown/text fallback。
- QQ 映射到 OneBot message segment；不支持的 segment 返回 fallback text 或 structured warning。
- `plugin://package` / `plugin://workspace` 继续经现有 media resolver 约束路径。

落地评估：优先级中，难度中高。需要跨 App Chat、QQ、conversation persistence 和 UI 展示一起收敛。

### P2-3 Tool Loop Agent / Agent 注册

JS surface：

```javascript
hostApi.registerAgent({
  key: "research-agent",
  tools: ["plugin.my_search", "web.search"],
  systemPrompt: "你是一个检索助手",
  handler: async (event, agent) => {
    return await agent.run(event.text)
  }
})
```

设计：

- Agent 是插件声明的 LLM orchestration preset，不是新平台 adapter。
- 复用 `RuntimeLlmOrchestratorPort`、centralized tool registry、ToolSource availability 和 provider runtime。
- 第一阶段只允许插件调用自己注册的 tools、host builtin tools 和当前 config/profile 允许的 ToolSource。
- Agent run 必须有 recursion depth、tool call count、token/cost、timeout 和 trace id。

落地评估：优先级低于 P0/P1，难度高。应在 `callLlm`、tool execution、fetch、provider read 都稳定后再做。

### P2-4 Filter OR / NOT 表达式

JS surface：

```javascript
hostApi.registerMessageHandler({
  filters: {
    anyOf: [
      { platformAdapterType: "onebot" },
      { eventMessageType: "group_message" }
    ],
    not: { permissionType: "blocked" }
  },
  handler: onMessage
})
```

设计：

- 保留当前 `declaredFilters: []` 线性 AND 行为作为兼容格式。
- 新增 filter AST：`allOf`、`anyOf`、`not`、`builtin`、`custom`。
- 编译阶段将旧格式转为 `allOf`，执行阶段短路求值。
- custom filter timeout 和 failure-stop 语义沿用现有 `PluginV2FilterEvaluator`。

落地评估：优先级低，难度低到中。它提升表达力，但不是插件生态可用性的第一阻塞。

## 分阶段落地建议

### Phase A：异步桥与权限底座

交付：

- `PluginV2HostApiAsyncBridge`
- `PluginV2HostApiFacade`
- permission policy / audit log / structured error
- QuickJS `await hostApi.*` 最小验证

验收：

- QuickJS handler 可 await 一个 fake host async API。
- timeout、permission denied、structured error 可测。
- architecture contract 确认没有新增 static DI 或 app direct runtime bypass。

### Phase B：P0 主动调用能力

交付：

- `hostApi.fetch`
- `hostApi.providers.list/models`
- 当前会话 `hostApi.message.send`
- 当前会话 `hostApi.conversation.history`

验收：

- 网络请求受 domain allowlist、timeout、body size 限制。
- provider 查询不泄露 secret。
- 当前会话发送在 App Chat / QQ 至少各有聚焦测试或 fake adapter 测试。
- history 不直连 DB，且 limit 上限生效。

### Phase C：LLM 与 context compress

交付：

- `hostApi.callLlm`
- usage / finishReason / provider/model 返回
- recursion guard
- `ContextStrategyToolSourceProvider.invoke()` 真正执行压缩

验收：

- 插件可直接调用 fake provider 并拿到文本与 usage。
- LLM hook 内调用 `callLlm` 不会递归触发同一批 hook。
- `compress_context` 不再返回 `context_compress_not_implemented`。

### Phase D：Cron / streaming / rich message

交付：

- `registerScheduledHandler`
- schedule lifecycle reconcile
- current-session streaming
- `PluginMessageSegment` 和 adapter fallback

验收：

- 插件启用、禁用、卸载、升级时 schedule 状态正确。
- scheduled wakeup 进入 V2 handler。
- streaming 对不支持编辑的平台有明确降级行为。
- rich message 在 App Chat / QQ 映射差异有合同测试。

### Phase E：Agent 与 filter 表达式

交付：

- `registerAgent`
- `agent.run`
- Agent tool allow policy
- filter AST

验收：

- Agent 有 tool-call 上限、timeout、cost guard。
- Agent 不能绕过 ToolSource availability。
- 旧 filter 注册完全兼容，新 AST 支持 OR / NOT。

## 风险

- QuickJS async bridge 是最大前置风险；若 Promise 等待不可控，所有主动宿主 API 都会变成不稳定能力。
- `callLlm` 有递归、成本和并发风险，必须默认绕过插件 LLM hook pipeline。
- rich message 与 streaming 在 App Chat / QQ 的能力不对等，必须设计 fallback，而不是假设 OneBot 能力在 App Chat 中天然存在。
- cron callback 会引入持久化生命周期问题，必须处理插件 disable、uninstall、upgrade。
- Agent 能力会放大工具调用、LLM 成本和权限问题，不应早于 P0/P1。
