## 背景与问题判断

当前项目的 NapCat 集成不是传统 APK 安装，也不是把运行文件放到公共外部存储后申请读写权限。当前链路是：

- `app/build.gradle.kts`：`targetSdk = 36`
- root `build.gradle.kts`：`ELYMBOT_MIN_SDK = 29`
- `app/src/main/AndroidManifest.xml` 已声明 `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_DATA_SYNC`、`POST_NOTIFICATIONS`，并将 `ContainerBridgeService` 声明为 `foregroundServiceType="dataSync"`
- `ContainerRuntimeInstaller` 将脚本、native runtime links、Ubuntu rootfs 和 runtime assets 准备到 app 私有 `filesDir/runtime`
- `ContainerRuntimeScripts.command(...)` 通过 `/system/bin/sh <script>` 启动脚本，避免直接 exec app 私有目录中的 shell 脚本
- `start_napcat.sh` 继续通过 proot 运行 `filesDir/runtime/rootfs/ubuntu` 内的 Ubuntu 用户态二进制，并无条件尝试绑定 `/sdcard` 与 `/storage/emulated/0`

因此，这个问题不应先按“补外部存储权限”处理。更可能的失效面是：

1. Android 10 / API 29 起 app 私有可写目录执行限制影响 rootfs 内二进制、proot loader 或子进程行为。
2. Android 11+ scoped storage 和不同 ROM 对 `/sdcard`、`/storage/emulated/0` 的访问策略使无条件 bind 失败。
3. Android 12+ 前台服务后台启动限制导致自动启动或后台启动 NapCat 失败。
4. Android 13+ 通知权限被拒后，前台服务通知可见性和用户感知变差，错误容易被误报为安装权限问题。
5. Android 14+ 前台服务类型和权限要求更严格，当前 manifest 已具备 `dataSync` 类型和权限，但运行时启动仍应明确处理异常和状态。
6. 厂商 ROM 可能限制 proot、seccomp、符号链接、子进程数量或长时间后台进程；没有真实设备时必须先用诊断分类降低盲修风险。

## 目标

本任务包目标是在无法覆盖真实低版本设备测试的前提下，让 NapCat 安装和启动链具备可诊断、可降级、可解释的兼容能力：

- 安装或启动失败时，能区分“外部存储 bind”、“rootfs / proot 执行”、“前台服务启动”、“网络安装”、“通知权限”这些不同原因。
- 不为 NapCat 盲目新增 `READ_EXTERNAL_STORAGE`、`WRITE_EXTERNAL_STORAGE`、`MANAGE_EXTERNAL_STORAGE` 或外部存储强依赖。
- 对低版本目标范围内的 API 29/30/31/32/33/34+ 采取分版本保护，但不降低 `targetSdk = 36`。
- 在无真机条件下，通过 JVM 单测、脚本合同测试、错误分类单测和 smoke command mock 覆盖主要兼容分支。
- 保持当前 feature-first、Hilt-only 和 core/feature 边界，不恢复 static runtime owner 或手写 subgraph。

## 非目标

- 不在本包内替换 NapCat upstream installer。
- 不在本包内实现新的 rootfs、proot 或 native binary 分发方案。
- 不把 NapCat 迁移到外部存储运行。
- 不绕过 Android 前台服务规则或通知权限。
- 不承诺没有真实设备的情况下完成端到端兼容验收。
- 不扩大 OneBot、QQ 消息链、插件 Host API、LLM 调度或登录业务行为。

## 方案比较

### 方案 A：只补权限声明和权限弹窗

做法是新增旧存储权限、All files access 或安装包权限提示。

优点：改动小，用户容易理解。

缺点：与当前运行链不匹配。NapCat 主链在 app 私有 `filesDir/runtime` 下运行，外部存储权限不能解决 proot/rootfs 二进制执行、前台服务启动、seccomp 或厂商 ROM 子进程限制。还会引入不必要的审核风险和用户信任成本。

结论：不采用。

### 方案 B：直接重构运行时，把 rootfs 或二进制移动到新位置

做法是改 native runtime、rootfs 布局或运行器位置，尝试绕开 Android 10+ 执行限制。

优点：如果定位准确，可能解决底层执行问题。

缺点：风险大，影响 container、voiceasset、runtime-audio 等共享容器使用者；没有真机时容易把一个 ROM 特定问题扩大成全局架构变化。当前还没有足够证据证明 rootfs 位置就是唯一根因。

结论：暂不采用，作为后续真机证据明确后的二期方案。

### 方案 C：预检诊断优先，脚本条件降级，版本化启动保护

做法是增加兼容性预检和错误分类，把启动前后的环境、权限、proot smoke、sdcard bind、前台服务启动结果写入现有 runtime state / log；脚本对外部存储 bind 做条件化处理；Android 12+ 自动启动和前台服务异常显式落状态。

优点：不依赖真实设备也能先完成大部分可测逻辑；不会新增无关危险权限；能把用户反馈中的“权限问题”拆成可定位类别；改动范围集中在 `core/runtime-container`、app service adapter、QQ bridge state adapter 和现有脚本合同。

缺点：第一期不一定直接修复所有 ROM 特例；真实设备仍需人工验证。

结论：采用。

## 推荐架构

推荐采用“诊断分类作为兼容入口”的架构：

1. 在 `core/runtime-container` 增加轻量 runtime compatibility probe，归属容器运行时，不进入 QQ domain。
2. `ContainerBridgeService.handleStartBridge()` 在 `ensureInstalled()` 后、`startNapCat()` 前执行预检。预检失败不一定全部阻断：硬失败阻断启动，软失败降级继续。
3. 预检结果通过 `RuntimeLogger` 记录，并用现有 `ContainerBridgeStatePort.markError(...)` / `markProcessRunning(...)` / `updateProgress(...)` 写出用户可见状态。第一期不新增持久化表。
4. `start_napcat.sh` 的 `/sdcard` 和 `/storage/emulated/0` bind 改成条件构造：路径存在且可读才加入 bind；失败只记录 warning，不阻断基础 proot smoke test。
5. `AndroidRuntimeBridgeController` 对 `startForegroundService` / `startService` 异常做分类日志：后台启动限制、权限/安全异常、service 不可用分别落不同消息。
6. `ContainerBridgeService` 的前台启动保持现有 `dataSync` 语义；如实现 API 级别允许，可使用 `ServiceCompat.startForeground(..., FOREGROUND_SERVICE_TYPE_DATA_SYNC)` 或同等兼容封装，让 Android 14+ 类型语义更显式。

## 诊断模型

新增模型应尽量局部化，避免污染 QQ API：

```text
RuntimeCompatibilitySnapshot
- sdkInt
- manufacturer
- model
- targetSdk
- appHome
- nativeLibraryDir
- scriptDirReady
- rootfsReady
- prootLinkReady
- loaderLinkReady
- systemShellReady
- appPrivateScriptReadable
- prootSmokeResult
- sdcardReadable
- externalStorageBindMode
- notificationPermissionState
- foregroundServiceStartMode
- category
- blocking
- userMessage
- technicalDetails
```

`category` 建议固定枚举：

- `READY`
- `ROOTFS_MISSING`
- `NATIVE_RUNTIME_MISSING`
- `APP_PRIVATE_EXEC_RESTRICTED`
- `PROOT_SMOKE_FAILED`
- `EXTERNAL_STORAGE_BIND_SKIPPED`
- `FOREGROUND_SERVICE_START_BLOCKED`
- `NOTIFICATION_PERMISSION_DENIED`
- `NETWORK_INSTALL_UNAVAILABLE`
- `ROM_PROCESS_RESTRICTED`
- `UNKNOWN`

第一期可以只把 snapshot 写入日志和 runtime state details，不必新增 Room 存储。若后续用户反馈需要上传诊断包，再进入单独设计。

## 启动流程

推荐流程：

1. 用户在 QQ / Runtime UI 发起启动，或 app 可见期触发 auto-start。
2. `AndroidRuntimeBridgeController.startBridge()` 使用当前 foreground service 路径启动 `ContainerBridgeService`。
3. `ContainerBridgeService.onCreate()` 立即创建 channel 并进入 foreground。
4. `handleStartBridge()`：
   - `markStarting()`
   - `containerRuntimeInstaller.ensureInstalled()`
   - `RuntimeCompatibilityProbe.runPreflight()`
   - 硬失败：`markError(snapshot.userMessage)`，追加技术日志，停止后续 start command
   - 软失败：`markProcessRunning(...)` 或 `updateProgress(...)` 记录降级状态，继续 `startNapCat()`
   - `startNapCat()` 后继续现有 health check / status check
5. `start_napcat.sh`：
   - 先运行已有 rootfs / proot smoke test
   - 条件添加外部存储 bind
   - bind 被跳过时写入 log，不影响 NapCat 安装基础链路
6. UI 继续消费 `NapCatRuntimeState.details` 和 progress 文案，不新增独立页面。

## 错误处理原则

- `Permission denied` 不能直接展示为“请授予存储权限”。必须结合失败点分类。
- 如果失败发生在 `/system/bin/sh <script>`：提示脚本入口不可读或系统 shell 调用失败。
- 如果失败发生在 proot smoke：提示当前系统可能限制容器运行，附带 SDK/ROM 和 proot stderr 摘要。
- 如果失败发生在 `/sdcard` bind：提示外部存储绑定已跳过或不可用，继续尝试基础启动。
- 如果失败发生在 foreground service：提示需要从应用前台启动，或检查后台启动限制。
- 如果通知权限被拒：不阻断 NapCat，但提示运行通知可能不可见。
- 如果网络 installer 下载失败：复用现有 `download-installer` / `installer-downloaded` progress 语义，归类为网络安装问题，不混成系统权限问题。

## 权限策略

本包默认不新增以下权限：

- `READ_EXTERNAL_STORAGE`
- `WRITE_EXTERNAL_STORAGE`
- `READ_MEDIA_IMAGES`
- `READ_MEDIA_VIDEO`
- `READ_MEDIA_AUDIO`
- `MANAGE_EXTERNAL_STORAGE`

理由：

- NapCat runtime 当前不依赖用户媒体库。
- app 私有内部存储不需要外部存储权限。
- `MANAGE_EXTERNAL_STORAGE` 与当前目标不匹配，且风险高。

保留并确认：

- `INTERNET`：NapCat upstream installer 和 apt / GitHub proxy 仍需要。
- `FOREGROUND_SERVICE`：容器前台服务需要。
- `FOREGROUND_SERVICE_DATA_SYNC`：Android 14+ data sync 前台服务类型需要。
- `POST_NOTIFICATIONS`：Android 13+ 通知权限，已有请求逻辑；拒绝时不应阻断启动。

`REQUEST_INSTALL_PACKAGES` 属于应用内更新链路，不应在本包中被解释为 NapCat runtime 所需权限。

## 测试设计

无真机条件下，测试重心放在可模拟分支：

- `RuntimeCompatibilityProbeTest`
  - rootfs 缺失 -> `ROOTFS_MISSING` blocking
  - proot link 缺失 -> `NATIVE_RUNTIME_MISSING` blocking
  - proot smoke stderr 包含 permission denied -> `APP_PRIVATE_EXEC_RESTRICTED` 或 `PROOT_SMOKE_FAILED`
  - `/sdcard` 不可读 -> `EXTERNAL_STORAGE_BIND_SKIPPED` non-blocking
  - 通知权限拒绝 -> `NOTIFICATION_PERMISSION_DENIED` non-blocking
- `ContainerBridgeServiceTest` 或现有 app unit test seam
  - preflight blocking 时不调用 `startNapCat()`
  - preflight non-blocking 时继续启动并写入 details
  - start command exception 时保留现有 markError 行为
- `AndroidRuntimeBridgeControllerTest`
  - Android O+ foreground start 分支仍保留
  - `SecurityException` / foreground start exception 写入分类日志
- `NapCatRuntimeScriptContractTest`
  - `start_napcat.sh` 不再无条件包含固定 `/sdcard` bind
  - 脚本包含条件 bind helper 和 warning log
  - proot smoke test 仍保留
- `AndroidManifestRuntimeContractTest`
  - `FOREGROUND_SERVICE_DATA_SYNC` 和 `foregroundServiceType="dataSync"` 保持存在

## 验收标准

本包完成时应满足：

- 用户看到的 NapCat 启动失败原因不再只有笼统的 `Permission denied`。
- 外部存储不可读或不可绑定不阻断基础 NapCat 安装尝试。
- Android 12+ 后台启动限制被记录为启动时机/前台服务问题，而不是 NapCat installer 问题。
- Android 13+ 通知权限拒绝不阻断启动，但状态可解释。
- Android 14+ 前台服务类型语义与 manifest 保持一致。
- 新增兼容代码仍通过 Hilt 注入，不新增 static owner / service locator。
- QQ / NapCat / OneBot 模块边界保持现状，QQ runtime 不反向依赖 app implementation。
- 相关合同测试和稳定节点构建通过，或明确记录未验证风险。

## 风险与后续验证

- 没有真实低版本设备时，不能证明 proot 在所有 API 29/30/31 ROM 上可用。
- Android 10+ app 私有可写目录执行限制如果实际命中 rootfs 内 ELF，第一期诊断只能准确分类，未必能修复。
- 厂商 ROM 的子进程、后台保活、seccomp 或 linker 行为可能需要单独适配。
- 如果用户反馈集中在某一 ROM，需要后续收集 `napcat.log`、runtime logger、SDK/ROM snapshot，再决定是否进入 `uth-debug`。
- 若诊断结果证明 rootfs 布局是根因，需要另开设计比较 nativeLibraryDir、noexec 分区、Termux-like runtime 或外部 helper 方案。
