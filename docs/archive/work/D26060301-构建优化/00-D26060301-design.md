# D26060301 构建优化设计

更新时间：2026-06-03 20:38 +08:00

## 场景

- Scene：`uth-design`
- Mode：`design-authoring`
- 目标：优化当前 Android 多模块项目的 Gradle 构建体验，优先降低配置阶段耗时、收窄高频验证入口的任务图，并改善 CI 串行等待。
- 输出：任务包 Design。源码实现、任务拆分、Worker prompt、验收评审和 Git 写入均不在本轮执行。

## 背景与问题

本任务来自 2026-06-03 的构建评估。当前项目已经使用较新的构建链：

- Gradle Wrapper：`9.4.1`
- Android Gradle Plugin：`9.2.0`
- Kotlin JVM / Compose plugin：`2.2.10`
- KSP：`2.3.8`
- Hilt：`2.59.2`
- Android 模块数量：66
- KSP 模块数量：22
- Hilt 模块数量：21
- Compose 模块数量：14

轻量诊断显示：

- `.\gradlew.bat help --console=plain --no-daemon --stacktrace` 配置阶段耗时约 50 秒。
- `help --configuration-cache` 能存储配置缓存，第二次复用后约 22 秒。
- `:app:testDebugUnitTest --dry-run` 有 1255 条任务线，其中约 219 条是 compile / jar 相关任务线。
- `:app:testDebugUnitTest --dry-run --configuration-cache` 能存储并复用配置缓存，第二次复用后约 22 秒。
- `:build-logic:check` 在全部 up-to-date 时仍约 39 秒，并提示可启用 configuration cache。

这些信号说明当前主要瓶颈不在单个库版本，而在：

- 配置缓存、构建缓存和并行执行没有成为默认构建能力。
- `:app:testDebugUnitTest` 被手工扩展成接近全仓模块编译入口。
- CI 分段串行，重复初始化 JDK / Android SDK / Gradle。
- 根构建脚本仍有 `subprojects`、`afterEvaluate`、`gradle.projectsEvaluated` 等后置配置写法，后续会增加 configuration cache 治理成本。

## 官方文档依据

按仓库 Context7 规则查询 Gradle 9.4.1 文档后，本设计采用以下官方口径：

- configuration cache 可通过 `org.gradle.configuration-cache=true` 或 CLI `--configuration-cache` 启用，用于缓存任务图。
- Gradle build cache 可通过 `org.gradle.caching=true` 或 CLI `--build-cache` 启用，用于复用任务输出。
- parallel execution 可通过 `org.gradle.parallel=true` 启用。

外部文档只作为工具行为依据；项目内验证入口、任务边界和治理规则仍以 `docs/context/01-验证构建治理.md`、`AGENTS.md` 和源码事实为准。

## 已知约束

- 不修改业务源码、DI、Manifest、版本号、发布配置或应用功能。
- 不删除 architecture 报告任务的强制刷新行为。`BuildBaselineContractTest` 明确要求 `architectureSourceRootsReport` / `architectureDebtReport` 保持 fresh。
- 不把 `clean assembleDebug` 从稳定节点验收中移除。仓库要求稳定节点必须确保 `.\gradlew.bat clean assembleDebug --console=plain --no-daemon --stacktrace` 无告警通过。
- 不默认升级 AGP、Gradle、Kotlin、KSP、Hilt 或 AndroidX 依赖。版本升级属于独立风险域。
- 不默认引入 Develocity、远程 build cache 或自托管缓存服务。本任务先做本地和 GitHub Actions 可控优化。
- 不把测试内部可见性问题用扩大 `-Xfriend-paths` 的方式继续放大；后续应逐步收窄或迁移到模块内测试。
- 不执行 Git 写入；后续提交、推送、PR 由 `uth-git` 处理。

## 方案比较

| 方案 | 结论 | 取舍 |
| --- | --- | --- |
| A. 只打开 Gradle 性能开关 | 可作为第一阶段 | 成本最低，预计能改善配置阶段和重复构建；但无法解决 app 单测任务图过大的根因 |
| B. 性能开关 + 配置脚本治理 | 推荐主线 | 在打开缓存的同时清理 `afterEvaluate` / `projectsEvaluated` 等配置热点，降低后续 cache 失效和任务图膨胀风险 |
| C. 全面重构测试结构和模块依赖 | 暂不作为本包主线 | 可能收益更大，但会触及大量测试归属、internal 可见性和模块边界，应在本包完成基线优化后另拆任务 |

本设计采用 B：先启用可验证的 Gradle 性能能力，再针对当前最明显的构建脚本热点做收敛，同时把 CI 并行和验证入口拆分纳入同一套验收。

## 目标状态

完成后应达到：

- 高频本地 Gradle 命令默认支持 configuration cache、build cache 和并行执行。
- `:app:testDebugUnitTest` 的任务图不再无条件拉起几乎所有 feature / core 模块的 compile jar 产物。
- module group 任务继续可用，但依赖解析改为 lazy task provider 或更明确的模块插件约定，不依赖全局 `projectsEvaluated`。
- `architectureCheck` 行为保持不变，architecture 报告仍每次 fresh。
- CI 能在不降低验证覆盖面的前提下减少串行等待和重复初始化成本。
- 构建优化有可复测的 before / after 指标，不只依赖主观体感。

## 设计主线

### 1. 建立构建基线指标

实现前先记录一组基线命令，避免优化完成后无法判断收益：

```powershell
.\gradlew.bat help --console=plain --no-daemon --stacktrace
.\gradlew.bat help --configuration-cache --configuration-cache-problems=warn --console=plain --no-daemon --stacktrace
.\gradlew.bat :build-logic:check --console=plain --no-daemon --stacktrace
.\gradlew.bat :app:testDebugUnitTest --dry-run --console=plain --no-daemon --stacktrace
.\gradlew.bat :app:testDebugUnitTest --dry-run --configuration-cache --configuration-cache-problems=warn --console=plain --no-daemon --stacktrace
```

记录项：

- wall time
- configuration cache 是否 stored / reused
- task line count
- compile / jar / ksp / hilt 相关任务数量
- warning / deprecated / exception / failed 文本扫描计数

这些指标写入后续验收记录，不写入本 Design。

### 2. 启用 Gradle 默认性能能力

建议在根 `gradle.properties` 增加：

```properties
org.gradle.configuration-cache=true
org.gradle.caching=true
org.gradle.parallel=true
```

迁移策略：

- 第一轮实现可先用 `org.gradle.configuration-cache.problems=warn` 作为过渡观测，只要验证命令没有问题再移除或保留为明确策略。
- CI 继续通过 `GRADLE_OPTS=-Dorg.gradle.daemon=false -Dorg.gradle.workers.max=2` 控制资源上限，不把本地 worker 上限硬编码进仓库根属性。
- 如果某个任务与 configuration cache 不兼容，优先修任务配置；只有确认为必须 fresh 的治理任务才保留显式不缓存行为。

### 3. 处理 build-logic 增量编译配置

`build-logic/gradle.properties` 当前为：

```properties
kotlin.compiler.execution.strategy=in-process
kotlin.incremental=false
```

设计建议：

- 移除或调整 `kotlin.incremental=false`，让 build-logic 回到 Kotlin 默认增量编译策略。
- 保留或移除 `in-process` 需要以 `:build-logic:check` 重复执行结果为准；不要只看单次耗时。
- build-logic 很小，因此这是低风险补强，不应作为唯一优化成果。

### 4. 收窄 app 单测任务图

当前 `app/build.gradle.kts` 中：

- `compileDebugUnitTestKotlin` 手写依赖多个模块的 `compileDebugKotlin`。
- `-Xfriend-paths` 拼接大量模块 build 输出。
- `testDebugUnitTest` 手写依赖几乎所有 `appUnitTestRuntimeProjects` 的 `compileDebugKotlin`、`bundleLibCompileToJarDebug`、`bundleLibRuntimeToJarDebug`。
- `classpath` 手工追加这些输出文件。

设计目标不是一次性迁移所有测试，而是先把这段配置变成可治理结构：

- 把 runtime project 列表拆成按测试类别命名的集合，例如 plugin host、QQ runtime、cron runtime、app shell。
- 只对真正需要跨模块 internal 可见性的测试保留 `friend-paths`。
- 能迁回模块自身测试的用例，后续进入独立开发任务，不在本包中大规模搬迁。
- dry-run 后验证 `:app:testDebugUnitTest` 任务线和 compile / jar 任务数量有下降，或者至少列表从“全仓默认”变为“按测试域显式”。

验收不要求立刻删除所有 friend path；要求它不再无边界增长。

### 5. 替换后置配置热点

根 `build.gradle.kts` 的 module group 当前通过 `gradle.projectsEvaluated` 查找每个子项目是否有 `assembleDebug` / `assemble` / `check`。设计建议：

- 优先改为在项目插件应用时注册或绑定任务依赖。
- Android application/library 模块使用 `plugins.withId("com.android.application")` 和 `plugins.withId("com.android.library")` 绑定对应 assemble task。
- JVM-only 模块保留明确的 `check` 绑定。
- 如果短期无法完全删除 `projectsEvaluated`，先把 `existingTaskPath` 和 module group 解析封装成受测试保护的 build-logic convention。

`app/build.gradle.kts` 中 `afterEvaluate` 用于 `assembleDebug` / `assembleRelease` 后导出 APK，也应改成直接 `tasks.named("assemble$capitalizedVariant").configure { finalizedBy(...) }`。该修改不改变产物路径和 artifacts guard。

### 6. CI 并行与缓存策略

当前 CI 分为：

- `tooling`
- `module-boundary-checks`
- `architecture-and-assemble`
- `app-tests`

设计建议：

- `tooling` 继续作为前置 guard，保留 wrapper、generated artifacts、`:build-logic:check`。
- `module-boundary-checks` 与 `app-tests` 可在 `tooling` 后并行执行，除非后续验证证明它们共享不可并行的生成物。
- `architecture-and-assemble` 继续包含 `clean architectureCheck assembleDebug`，作为最终 debug 构建 gate。
- 所有 Gradle job 使用同一套 configuration cache / build cache 策略，先用 warning 观测，再切到严格失败。

CI 不应为了提速移除 `clean architectureCheck assembleDebug`。优化方向是并行和缓存，而不是降低 gate。

## 验证设计

实现完成后至少运行：

```powershell
.\gradlew.bat :build-logic:check --console=plain --no-daemon --stacktrace
.\gradlew.bat :app:testDebugUnitTest --dry-run --configuration-cache --configuration-cache-problems=warn --console=plain --no-daemon --stacktrace
.\gradlew.bat architectureCheck --configuration-cache --configuration-cache-problems=warn --console=plain --no-daemon --stacktrace
.\gradlew.bat clean assembleDebug --console=plain --no-daemon --stacktrace
```

如果修改 CI，还需要通过 GitHub Actions 或等效本地命令确认：

- tooling gate pass
- module boundary checks pass
- architecture and assemble gate pass
- app debug unit tests pass

验收扫描：

- `warning`：0，或列明并经用户确认临时 waiver。
- `deprecated`：0，或列明来源和处理计划。
- `exception` / `failed`：0。
- configuration cache：目标任务至少能 stored；高频任务第二次能 reused。

## 风险与回退

| 风险 | 表现 | 回退 |
| --- | --- | --- |
| configuration cache 暴露任务配置不兼容 | 构建输出 configuration cache problem | 先改对应任务；必要时对单个命令临时禁用并记录 |
| parallel execution 暴露共享输出目录竞争 | CI 偶发失败或 artifacts 被覆盖 | 为共享输出任务声明 inputs / outputs，或保留串行依赖 |
| app 单测 classpath 收窄导致测试找不到类 | `NoClassDefFoundError` / 编译失败 | 恢复对应测试域依赖，并把该测试域列入显式集合 |
| build-logic 增量配置变化收益不明显 | 耗时无改善 | 保留默认配置，不把它作为主收益 |
| CI 并行后总资源不足 | job 超时或 worker 争用 | 保持 `workers.max=2`，必要时只并行 app-tests 与 module-boundary-checks |

## 非目标

- 不做全项目依赖版本升级。
- 不迁移全部 app 单测到 feature 模块。
- 不引入远程 build cache、Develocity 或第三方分析插件。
- 不修改 architecture allowlist 口径。
- 不修改 release APK 导出目录或 artifacts 提交流程。
- 不压缩 `clean assembleDebug` 验收要求。
